## 1. 概要

信頼されたメンバーのみが参加できる L2 オーバーレイネットワークを構築する。トランスポートに WireGuard フルメッシュ、データプレーンに VXLAN(単一 VNI)、コントロールプレーンに EVPN(iBGP フルメッシュ)を用いる。メンバーの参加・退去は、全既存メンバーの署名(N-of-N)を必要とする分散型メンバーシップ台帳で制御する。

本ネットワークは既存の「闇ネット」(tinc ベース L2 VPN)とは独立した別系統として構築する。

### 1.1 設計目標

- 信頼されたメンバーのみが L2 セグメントに参加できること。認可されないノードはトランスポート層(WireGuard)にすら接続できない。
- メンバーの追加・削除には既存全メンバーの同意(N-of-N)を要すること。
- 任意の単一拠点が停止しても、残るノード間の通信は継続すること。
- メンバーシップ変更の可用性をネットワークの稼働状況に依存させないこと(署名収集はオフバンドで実施)。

### 1.2 非目標

- 中央コーディネータ/ルートリフレクタによる管理(分散・対等を優先するため採用しない)。
- M-of-N 閾値署名(本設計では純粋な N-of-N を採用する)。
- L3 ゲートウェイ機能(IRB)、複数 L2 セグメント(将来拡張として保留)。

## 2. アーキテクチャ

### 2.1 レイヤー構成

```
┌──────────────────────────────────────────────────┐
│ コントロールプレーン: EVPN (iBGP フルメッシュ)         │
│   AFI/SAFI: L2VPN/EVPN (25/70)                      │
│   Type-2: MAC/IP 広告   Type-3: IMET (BUM 配送先)    │
├──────────────────────────────────────────────────┤
│ データプレーン: VXLAN (vxlan0, 単一 VNI)              │
│   ブロードキャストドメイン 1 つ、全ノードがフラットに参加  │
├──────────────────────────────────────────────────┤
│ トランスポート: WireGuard フルメッシュ (wg0)           │
│   overlay /32 が iBGP/VXLAN の通信路となる            │
├──────────────────────────────────────────────────┤
│ 認可: メンバーシップ台帳 (Ed25519 署名チェーン, N-of-N) │
│   確定した wg 公開鍵と overlay IP のみが参加可能         │
└──────────────────────────────────────────────────┘
```

### 2.2 依存の向き(重要)

各レイヤーは下位レイヤーに依存する。

1. メンバーシップ台帳が、あるノードの WireGuard 公開鍵と overlay IP を **確定(commit)** する。
2. 確定したノードのみが WireGuard ピアとして設定に反映され、フルメッシュに参加できる。
3. WireGuard overlay 上でのみ iBGP セッションが確立できる。
4. iBGP/EVPN に載れたノード間でのみ VXLAN データプレーンが成立する。

したがって、台帳で認可されない限りトランスポート層に到達できず、L2 セグメントにも到達できない。「信頼メンバー限定」がトランスポート層で物理的に保証される。

## 3. メンバーシップ台帳(認可レイヤー)

### 3.1 データモデル

台帳は append-only のエントリ列。各エントリは 1 つの変更提案を表し、確定には全既存メンバーの署名を要する。

```
Entry {
  seq:        u64              // 単調増加するシーケンス番号
  prev_hash:  [32]byte         // 直前の確定エントリのハッシュ(チェーン構造)
  op:         ADD | REMOVE
  subject: {
    node_id:    string         // ノード識別子(一意)
    wg_pubkey:  [32]byte       // WireGuard 公開鍵
    endpoint:   string         // ip:port(可変。下記 3.4 参照)
    overlay_ip: 10.99.0.x/32   // overlay 上のアドレス
  }
  approvals:  map<node_id, Ed25519Sig>   // 既存メンバー全員の署名が揃って確定
}

entry_hash  = SHA256( seq ‖ prev_hash ‖ op ‖ canonical(subject) )
approval[i] = Ed25519_sign( member_priv[i], entry_hash )
```

`canonical(subject)` は subject フィールドの決定論的シリアライズ(キー順固定の正規化エンコード)とする。全ノードで同一バイト列になることが必須。

### 3.2 確定(commit)ルール — N-of-N

各ノードはローカルで台帳全体を replay し、以下を満たすエントリのみを反映する。中央の確定者は存在せず、全員が同一の決定論的ルールで同一の結論に至る。

```
M = 確定済み台帳から導出される現在のメンバー集合

op == ADD の場合:
    approvals のキー集合 ⊇ M               // 既存全員が署名

op == REMOVE の場合:
    approvals のキー集合 ⊇ M \ {対象ノード}  // 退去対象を除く全員が署名
```

### 3.3 ブートストラップ

- 最初の 1 ノードは「メンバー集合 = {自分}」のため自己署名で確定する。
- 既存の信頼メンバー群(例: 30 ノード規模)を一度に立ち上げる場合、N-of-N を逐次適用すると O(N²) の署名コストになるため、**初期メンバー全員を 1 つの genesis エントリにまとめて投入し、それを全員が一度だけ署名して確定**させる。
- genesis 以降の追加・削除は通常の N-of-N フローに従う。

### 3.4 endpoint の扱い

`endpoint`(物理 IP:port)は回線事情で変動しうる。これを署名対象に含めると変更のたびに N-of-N が必要になり運用が破綻するため、**endpoint は署名対象 `canonical(subject)` から除外**し、wg_pubkey・overlay_ip・node_id のみを認可対象とする運用を推奨する。endpoint の更新は WireGuard 側のローミング(または別途の軽量な配布)で吸収する。

> 実装メモ: endpoint を署名対象に含めるか否かは確定すること。除外する場合、上記 `canonical(subject)` の定義から endpoint を外す。

### 3.5 署名収集(オフバンド)

署名収集はネットワークの稼働状況に依存させない。これにより N-of-N の厳密性を保ったまま、ノード停止時でも(復帰後に署名を追加することで)メンバーシップ変更が可能になる。

フロー:

1. 変更提案者がエントリ `(seq, prev_hash, op, subject)` を作成する。
2. 各メンバーへ任意の手段(別 VPN、メッセンジャー、USB、対面等)でエントリを回送する。経路の信頼性は不要。
3. 各メンバーが `entry_hash` を検証し `Ed25519_sign(priv, entry_hash)` を返す。
4. 全署名(N 個)が揃ったら、誰かが束ねて確定版エントリを配布する。
5. 各ノードがローカルで replay・検証し、WireGuard/FRR 設定を再生成する。

署名は `entry_hash` に対するものであり、改竄されれば hash が一致せず棄却される。順序は `prev_hash` チェーンで保証される。**収集経路は完全に信頼不要**。停止中ノードの署名は復帰後に追加すればよく、確定の遅延はデータプレーンに一切影響しない。

## 4. WireGuard トランスポート

### 4.1 トポロジ

全ノード間フルメッシュ(論理)。N ノードで N(N-1)/2 セッション(例: 30 ノードで 435)。台帳が single source of truth となり、各ノードの WireGuard peer 設定は台帳の確定メンバーから生成する。

ただし WireGuard は「少なくとも片側が到達可能な endpoint を持つ」ペアでしか直接セッションを張れない。各ノードを到達性で 3 種に分類し、直接張れないペアは §4.4 の NAT 越えで補完する。論理フルメッシュ(= 全ペアが何らかの経路で疎通する状態)は維持する。

| 区分 | 説明                                   | 待ち受け                          |
|------|----------------------------------------|-----------------------------------|
| A    | グローバル IP(固定/安定)を持つ          | 可能。リレー兼待ち受け点を兼ねる    |
| B    | NAT 配下。A とは自分から張りに行ける       | 不可。A 宛てに発呼                 |
| C    | NAT 配下同士のペア(B-B)                 | §4.4 で対処                       |

**前提: A は常に 1 台以上存在する。** これによりリレー先が常に確保され、いかなる B-B ペアも最終的に疎通可能となる(原理的に「永久に繋がらない」ペアが生じない)。結果として、フルメッシュ iBGP の前提である「全ノードが全ノードから直接 Type-2 を受ける」(§7.2)が崩れない。

### 4.2 アドレッシング

- overlay subnet: `10.99.0.0/24`(例。確定すること)
- 各ノードに台帳上で `/32` を割り当てる。この overlay IP が iBGP の neighbor アドレスかつ VXLAN の local アドレスとなる。

### 4.3 設定要点

- 各 peer の `AllowedIPs` は当該ノードの overlay `/32` のみ(L2 は VXLAN で運ぶため、wg 層では overlay の到達性のみを扱う)。
- `PersistentKeepalive = 25`(NAT 越えのため。BFD とは目的が異なり併用する)。
- wg0 の MTU は §6 に従い明示設定する。

### 4.4 NAT 越え(ホールパンチ + リレー)

到達性区分(§4.1)ごとに接続方式が異なる。Tailscale 型の二段構え(まず直接接続、不可ならリレー)を採用する。

**A 宛て(B→A, A→A)**
A は到達可能 endpoint を持つため、相手は A 宛てに発呼するだけで張れる。B は NAT 穴を `PersistentKeepalive` で維持する。

**B-B(C 区分)— 段階的に接続を試みる**

1. **直接接続(ホールパンチ)を試行する。** 両 B が、外から見た自分の ip:port(NAT 後のアドレス)を取得し、シグナリング経由で交換、ほぼ同時に互いへ送出して双方の NAT に穴を開ける。成功すれば以降は直接の wg セッションとなり、A の帯域を消費しない。
   - シグナリングは台帳配布経路(§3.5)に相乗りさせず、軽量な専用チャネルとして設けてもよい。実装方針は要確定(§8)。
   - Symmetric NAT(外向きポートが宛先ごとに変わる NAT)が相手だと予測が外れ成功率が落ちる。失敗時は次段へフォールバック。

2. **リレー(A 経由)へフォールバックする。** 直接張れない B-B ペアは、A ノードを中継して wg パケットを運ぶ。A が常に 1 台以上いる前提(§4.1)により、このフォールバックは常に成立する。
   - リレーは wg パケットを転送するだけであり、**iBGP/EVPN から見れば B-B は通常どおり直接疎通しているように見える**(Type-2 の伝播に影響しない)。
   - 当該経路のみ A の帯域とレイテンシに乗る。複数 A がいる場合は分散・冗長化の余地がある。

**役割の非対称(設計判断として明示)**
A ノードは「対等なメンバー」であると同時に「リレー兼待ち受け点」という運用上の役割を暗黙に背負う。帯域・可用性の要求が B より高くなる。台帳のメンバーシップ(対等)とトランスポートの役割(非対称)は別レイヤーの概念であり、混同しないこと。

## 5. VXLAN データプレーン + EVPN コントロールプレーン

### 5.1 VNI 設計

単一 VNI / 単一 L2 セグメント。全ノードが同一ブロードキャストドメインに参加するフラット構成。

- VNI: `10000`(例。確定すること)
- dstport: `4789`(標準。wg がさらに UDP カプセル化する)
- L3 ゲートウェイ(IRB)・VRF・Type-5 は使用しない。

### 5.2 Linux インターフェース設定

```sh
ip link add vxlan0 type vxlan id 10000 dstport 4789 \
    local <overlay_ip> nolearning
bridge link set dev vxlan0 neigh_suppress on learning off
```

- `nolearning` / `learning off`: データプレーンでの MAC 学習を無効化し、MAC 学習は EVPN(FRR)に委ねる。FRR が受信した Type-2 を FDB / neighbor table に programming する。
- `neigh_suppress on`: ARP/ND 抑制。EVPN の MAC/IP 広告を元に各ノードがローカルで ARP 応答するため、wg 越しの BUM トラフィックを削減できる。

### 5.3 EVPN / iBGP(FRR)

- iBGP フルメッシュ。全ノード同一 ASN(プライベート ASN を確定すること)。
- neighbor は各ノードの overlay IP。neighbor 設定は台帳から生成する。
- 単一 VNI のため `advertise-all-vni` で十分。

FRR 設定骨子:

```
router bgp <ASN>
  neighbor <peer_overlay_ip> remote-as <ASN>
  neighbor <peer_overlay_ip> bfd
  ! ... 全 peer 分を台帳から生成 ...

  address-family l2vpn evpn
    neighbor <peer_overlay_ip> activate
    advertise-all-vni
  exit-address-family
```

- Type-2(MAC/IP)で MAC を広告し合い、Type-3(IMET)で BUM 配送先を管理する。
- BUM トラフィックは head-end replication で IMET の配送先リストへ unicast 複製される。

### 5.4 闇ネットとの分離

- 別ポート・別鍵の WireGuard インスタンス上に別 VXLAN を載せるため、論理的に分離される。
- 事故防止のため、本ネットワークの wg0 / vxlan0 / bridge を **専用の network namespace** に収容し、闇ネットと物理的に分離することを推奨する。

### 5.5 単一 L2 の留意点

30 ノード超が同一ブロードキャストドメインに乗るため、BUM フレーム 1 つが wg 上で N-1 本の unicast に複製される。ARP suppression により日常の ARP は抑制されるが、DHCP・mDNS・SSDP 等のブロードキャスト/マルチキャストが多いノードがあると負荷が増える。問題化した場合は VNI 分割(複数セグメント化)で対処する。現時点では単一 VNI とする。

## 6. MTU 設計

二重カプセル化により MTU が削られる。各層で正しい値を明示設定し、過大フレームの暗黙のドロップ/フラグメントを防ぐ。

### 6.1 オーバーヘッド積み上げ(下層 IPv4・物理 1500 の場合)

```
物理 MTU                                       1500
  ├ WireGuard カプセル化           -60   →      1440   (wg0 MTU)
  │   IPv4 20 + UDP 8 + wg header 32
  └ VXLAN カプセル化               -50   →      1390   (vxlan0 MTU)
      outer IP 20 + UDP 8 + VXLAN 8 + inner Ethernet 14
```

### 6.2 設定値

| 下層           | wg0 MTU | vxlan0 MTU |
|----------------|---------|------------|
| IPv4 / 物理1500 | 1440    | 1390       |
| IPv6 / 物理1500 | 1420    | 1370       |

- 下層が IPv6 の場合、outer IP が 40B となり wg のオーバーヘッドは 80B。
- MAP-E・PPPoE 等で物理 MTU が 1500 未満の環境では、実測値から引き算すること。
- vxlan0 をブリッジに収容する場合、ブリッジおよびその先の tap/接続インターフェースもすべて vxlan0 と同じ値に揃える。**1 箇所でも大きいままだと、そのインターフェース起点のフレームのみ MTU 超過で詰まる。**

### 6.3 下層 MTU の実測手順

WireGuard を張る前に、物理対向エンドポイント宛てに DF 付き ping で実効 MTU を確認する。

```sh
ping -M do -s 1472 <peer_physical_ip>   # 1472 + 28(ICMP+IP) = 1500
# 通らなければ -s を下げ、通る最大値を探す。それが下層実効 MTU。
```

得られた実効 MTU から、wg0 = 実効 - 60(IPv6 は -80)、vxlan0 = wg0 - 50 を算出して設定する。

## 7. 障害時の挙動と BFD

### 7.1 単一拠点停止

フルメッシュ iBGP は単一障害点を持たない。任意の 1 拠点が停止しても、残るノード間の iBGP セッションは維持され EVPN 経路も流れ続ける。停止ノード宛ての MAC/IP は Type-2 が撤回され到達不能になるが、他ノード同士の通信は影響を受けない。

### 7.2 部分分断(留意点)

iBGP はループ防止のため経路を再広告しない。フルメッシュは各ノードが全ノードから直接 Type-2 を受ける前提で成立する。したがって特定 2 ノード間の wg セッションのみが切れると、その 2 者間の MAC が相互に不明となる(他は正常)。

恒常的な NAT 起因の B-B 不通については、§4.4 のリレー(A 経由)により疎通が保証されるため、この前提は満たされる。一方、リレー先である A の障害や、回線断による一時的な分断は依然として発生しうる。これらは §7.3 の BFD で速やかに検出し、別経路(他の A 経由のリレー等)へ収束させる。複数 A を用意するとリレーの冗長性が高まる。

### 7.3 BFD

iBGP セッションは wg 上を流れるため、wg パス断は最終的に BGP 断につながるが、BGP デフォルトの hold timer(180 秒)は長い。BFD を併用し収束を高速化する。

```
bfd
  peer <peer_overlay_ip>
    transmit-interval 300
    receive-interval 300
    detect-multiplier 3        ! 約 900ms で down 判定
```

- wg の `PersistentKeepalive`(NAT 穴維持)と BFD(経路死活速報)は目的が異なり、両方設定する。
- 300ms × 3 は 30 ノード超のフルメッシュでは送出パケットが増えるため、負荷が気になる場合は 1 秒間隔へ緩和してよい(実用上問題なし)。

## 9. スコープ外(将来拡張)

- 台帳 → wg/FRR 設定のコード生成(別途実装。台帳を single source of truth とする方針のみ確定)。
- 複数 L2 セグメント(VNI 分割)。
- M-of-N 閾値署名による可用性緩和。
- L3 ゲートウェイ(IRB)機能。
